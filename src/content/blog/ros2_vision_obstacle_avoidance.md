这套项目断断续续写了四天，从只有一个 README 的空仓库，一路做到 v3.0 的五臂对比基准。中间经历了从 ROS 2 Humble 迁移到 Jazzy、从 Gazebo classic 迁移到 Harmonic 的整个换栈过程。

但最让我有收获的，不是"又学会了几个包"，而是终于想明白了一个问题：**为什么避障系统要长成"感知—决策—控制"三层，而不是写一堆 if-else 就完事？**

答案也很朴素：因为每一层要回答的问题根本不同。

- **感知**回答"哪里能走"——它不该关心车要怎么转；
- **决策**回答"往哪走"——它不该关心像素怎么算；
- **控制**回答"走多快、转多猛"——它不该关心地图长什么样。

一旦把这三件事混在一个函数里，调试就会变成玄学：车撞了，你分不清是看不见、还是判断错、还是转太慢。

下面按这个分层，把这四天踩过的路重走一遍。

## 一、先让小车在 Gazebo 里跑起来

第一步是建模。用 xacro 写差速底盘：车身 `base_link`、左右驱动轮、前后支撑轮、单目相机，再加 Gazebo 的差速驱动插件。

这里最容易踩的坑不是语法，而是**参数必须和模型严格对齐**：轮距写成 0.22、轮径写成 0.1，就必须和 URDF 里轮子的实际位置、半径完全一致。差 1cm，车走起来就会画圈，而且你很难第一眼怀疑到插件参数上。

相机也有一个隐蔽的约定：图像消息的 `frame_id` 要和下游节点约定的坐标系一致，所以必须单独建一个光学坐标系，并加标准旋转：

```xml
<link name="camera_link_optical"/>
<joint name="camera_optical_joint" type="fixed">
  <parent link="camera_link"/>
  <child link="camera_link_optical"/>
  <origin xyz="0 0 0" rpy="-1.5707 0 -1.5707"/>
</joint>
```

当时理解了一句话：**URDF 不是"配置文件"，是"机器人图纸"**。图纸错了，后面的控制再精巧也是在错误的几何上运行。

## 二、把图像变成"能不能走"

感知的第一版非常传统：灰度化 → 亮度阈值二值化 → 裁 ROI → 横向三分 → 统计白像素占比。

```python
def compute_zone_scores(bgr_img, gray_threshold, roi_bottom_ratio):
    """输入 BGR 图像，返回 (左, 中, 右) 三个区域的可通行率（0~1）。"""
    h, w = bgr_img.shape[:2]

    gray = cv2.cvtColor(bgr_img, cv2.COLOR_BGR2GRAY)
    _, binary = cv2.threshold(gray, gray_threshold, 255, cv2.THRESH_BINARY)

    roi_top = int(h * (1.0 - roi_bottom_ratio))
    roi = binary[roi_top:h, :]

    third = w // 3
    zones = (roi[:, :third], roi[:, third:2 * third], roi[:, 2 * third:])

    return tuple(float(np.count_nonzero(z)) / z.size for z in zones)
```

有三个设计决定，事后看都是对的：

1. **只取画面底部 40%**。远处的像素受透视和光照影响大，真正决定"下一秒会不会撞"的是近处地面。
2. **横向三分，而不是整幅图算一个值**。决策需要知道的是"左边能不能走"，不是"整体亮不亮"。整幅图平均会把一个挡住正前方的箱子稀释成"85% 可通行"。
3. **写成不依赖 ROS 的纯函数**。这一点后来救了命：82 条 pytest 单测里，绝大部分不需要启动 Gazebo 就能跑，改阈值、改 ROI 立即能验证。

## 三、决策层：不抖，比聪明更重要

第一版决策很"聪明"：哪边分高往哪边走。结果车在障碍物边缘疯狂左右横跳——因为分数在阈值附近抖动。

真正解决问题的不是更复杂的算法，而是三条约束：

- **双端滞回**：可通行率 > 0.7 才允许直行，< 0.3 才判定必须停，中间保持上一状态；
- **斜坡平滑**：角速度不直接跳变，而是每周期最多变化 2.0 rad/s²，避免"猛甩头"；
- **看门狗**：图像超过 1 秒没来就强制停车。

第三条最容易被忽略，但它的语义很重要：**没消息 ≠ 安全**。传感器断了、节点崩了、桥接挂了，系统默认动作必须是停车，而不是保持上一次指令继续冲。

## 四、单目的硬伤：0.34 米的视觉盲区

做完上面这些，直线场景已经能过，但一加"需要绕行"的场景就露馅。

排查后发现是几何问题：相机装在 0.08m 高，ROI 又只取底部 40%，算下来**正前方约 0.34m 是视觉盲区**——障碍物贴到脸上时，它在画面里已经掉出 ROI 了。视觉看到的是"前方一片白"，然后安心撞上去。

这就是加 2D 激光雷达的直接原因。但雷达怎么和视觉融合？

我试过加权平均，结论是**安全类判断不能用平均值**：

> 视觉说"可通行率 0.9"，雷达说"正前方 0.2m"，平均一下得到一个"还行"的结论——这就是事故的来源。

最后采用**安全闸门**：雷达只做两件事——近距离硬否决、远距离兜底。

```python
def fuse_scores(zone_scores, sector_dists, safety_distance,
                lidar_clear_floor=0.5, lidar_clear_distance=1.0):
    fused = []
    for score, dist in zip(zone_scores, sector_dists):
        if math.isfinite(dist) and dist < safety_distance:
            fused.append(0.0)            # 近距硬墙：直接否决
        elif not math.isfinite(dist) or dist > lidar_clear_distance:
            fused.append(max(score, lidar_clear_floor))  # 雷达确认无障碍，给视觉兜底
        else:
            fused.append(score)          # 中距离，视觉主导
    return tuple(fused)
```

参数上有一个必须满足的约束：**闸门距离必须大于视觉盲区**。盲区 0.34m，闸门就取 0.5m，同时给 0.2m/s 的巡航速度留出转向余量。否则会出现"雷达还没报警，视觉已经看不见"的危险夹层。

另外把雷达的 360° 砍成前方 60°，与相机 FOV 对齐，再均分左/中/右三个扇区取最小距离。这样两路感知的"左中右"语义一一对应，融合时不需要额外的坐标变换。

## 五、全局问题：Nav2 与 SLAM

反应式避障只能看眼前。要做"从 A 点到 B 点"，就得上全局规划。

第一版是经典组合：静态地图 + AMCL 定位 + DWB 局部控制。跑通之后立刻发现一个工程上的硬伤：**每次改 world（挪一个箱子）都要重新手绘 9m × 9m 的地图**。仿真迭代成本高得离谱。

于是换成 SLAM Toolbox 在线建图：订阅 `/scan` 和 `odom->base_link`，发布 `map->odom` 和 `/map`，Nav2 的静态层直接吃这张实时地图。改场景再也不用画图了。

这一段踩了两个很典型的坑：

| 现象 | 根因 | 处理 |
|---|---|---|
| 全局规划恒定返回空路径 | NavFn 单次规划上限约为地图宽度的 2 倍（迷宫地图 7.1m → 上限 14.2m，实际路线 22m） | 换 `SmacPlanner2D` |
| 1.1m 窄走廊里原地反复微转、频繁触发恢复行为 | DWB 的弧线采样在窄走廊找不到可行解 | 换 `RegulatedPurePursuitController`，拐角先原地对正 |

这两个坑让我记住了一件事：**默认参数不是通用参数**。Nav2 的默认组合在开阔场地很好用，但一到窄空间和长路线就会静默降级，日志里只有一句含糊的 "Failed to make progress"。

## 六、迷宫：反应式的边界在哪

为了搞清楚"不依赖地图到底能走多远"，做了一个 5×5 完美迷宫：唯一出口在东侧，机器人不启动 Nav2、不下发目标点，只靠雷达和视觉自己走出去。

控制律最后简化成三句话：

1. **贴右墙走**：用右前方 45° 的距离做比例控制，墙近了左偏、墙远了右偏；
2. **遇墙选边**：正前方 < 0.6m 时，比较左右各 125° 大扇区的最远距离，朝更开阔的一侧原地转；
3. **转向带滞回**：一旦开始转，必须转到正前方 > 1.0m 才恢复直行。

第三条是实测逼出来的。最初是"前方 < 0.6m 就转"，结果在墙角反复"转一下、往前蹭一点"，最后卡死。加入滞回后，154 秒走出迷宫，全程 22m，无碰撞。

这个实验的价值不在迷宫本身，而在于它给出了反应式的边界：**只有局部观测时，贴墙策略能保证"走出去"，但不保证"走得短"**——22m 对 Nav2 的 17.7m，多走了 25%。

## 七、用五条臂把"感觉"变成数字

到这一步，手里已经有一堆方案了，但"哪个更好"全靠嘴说。于是写了自动基准：5 个场景 × 5 条臂，一条命令起停 Gazebo 和 Nav2，自动采集指标、出表出图。

五条臂刚好覆盖五种"传感器 × 规划"的组合：

| 臂 | 传感器 | 规划 |
|---|---|---|
| 纯 OpenCV | 单目相机 | 无（反应式） |
| 纯雷达 | 2D 雷达 | 无（反应式） |
| 视觉+雷达 | 相机 + 雷达 | 无（反应式） |
| Nav2 | 雷达 | 全局规划 + 局部控制 |
| Nav2+视觉护栏 | 雷达 + 相机 | 全局规划 + 视觉兜底 |

实测结果（每格 1 次）：

| 场景 | 纯 OpenCV | 纯雷达 | 视觉+雷达 | Nav2 | Nav2+视觉护栏 |
|---|---|---|---|---|---|
| detour_test | 失败（碰撞 2） | 54.6s / 9.53m | 62.3s / 9.93m | 23.1s / 4.48m | 23.3s / 4.52m |
| obstacle_course | 25.9s / 4.90m | 25.8s / 4.90m | 26.0s / 4.90m | 25.1s / 4.93m | 25.2s / 4.94m |
| low_contrast_course | 25.8s / 4.90m | — | 25.9s / 4.90m | 25.0s / 4.92m | — |
| dim_course | 26.0s / 4.90m | — | 26.0s / 4.90m | 25.1s / 4.93m | — |
| maze_course | — | 154.2s / 22.18m | 153.9s / 22.21m | 92.7s / 17.71m | 92.1s / 17.67m |

三条结论：

1. **结构化直线场景，反应式和 Nav2 打平**（都在 26s 左右）。说明不是"上了 Nav2 就一定更好"，问题复杂度决定方案。
2. **差距出现在需要全局信息的地方**。绕行场景 Nav2 快 2.7 倍，迷宫快 40%——因为它们知道"终点在哪、哪条路更短"。
3. **纯视觉的失败点非常具体**：detour_test 里连续 2 帧出现 < 0.13m 回波。原因就是盲区——绕行时车头离箱子太近，画面里看不到，雷达却已经贴上了。

指标不只看成功率，还包括：到达时间、路程、最小间距、碰撞次数、卡死占比、角速度 jerk（衡量控制平滑度）、CPU 占比。比如 hybrid 臂和纯 Nav2 耗时几乎一样（46.9s vs 47.0s），但 CPU 占比略高（3.21 vs 2.99）——这就是"视觉护栏"的真实开销，平时不介入，只在危险距离兜底。

需要诚实说明：目前每格只跑了 1 次，样本量不足以下强结论，下一步应该扩到 3 次取均值。

## 八、一路踩过的坑

| 坑 | 现象 | 根因 | 处理 |
|---|---|---|---|
| 相机 `frame_id` 不匹配 | 下游节点收到图像但坐标对不上 | 缺光学坐标系 | 单独建 `camera_link_optical` + 标准 rpy |
| 视觉盲区 | 贴脸障碍看不见 | 相机 0.08m 高 + ROI 底部 40% | 闸门距离 0.5m > 盲区 0.34m |
| 雷达扇区左右反了 | 该左转时右转，直接撞 | 角度正方向 = 机器人左侧 | 按角度符号重排左/中/右 |
| 贴障卡死 | 擦着障碍走不动 | 直行时侧向距离过近 | 侧身护卫 0.25m，禁止直行 |
| 墙角抖动 | 转一下、蹭一下、卡死 | 没有转向滞回 | 0.6m 进入转向、1.0m 才退出 |
| Humble 迁移 Jazzy | `gazebo_ros` 包不存在 | Ubuntu 24.04 没有 Humble 二进制 | 改用 `ros_gz_sim` + `parameter_bridge` |
| `gz sim` 开 GUI 段错误 | 一开界面就崩 | `--headless-rendering` 与 EGL 冲突 | headless 只加 `-s`，不加渲染参数 |
| Nav2 生命周期偶发超时 | 目标被拒绝、TF 串扰 | 残留旧进程占着同一 ROS_DOMAIN_ID | 跑基准前确认无残留 `gz sim` / `nav2_*` |

## 结语：分层不是形式主义

四天做下来，最深的体会是：**避障系统的难点从来不是"识别障碍物"，而是"在不确定的情况下做保守的决定"**。

- 视觉阈值会误判，所以需要雷达兜底；
- 雷达会有噪点，所以需要视觉提供语义；
- 两路都可能掉线，所以需要看门狗；
- 局部策略能走出去，但走不短，所以需要全局规划；
- 全局规划依赖地图，所以需要 SLAM 或先验地图。

每一层都在补上一层的洞，而每一层又都有自己的洞。所谓"系统设计"，就是承认这些洞的存在，然后让最坏情况仍然是安全的。

如果下次有人问我"到底该用反应式还是 Nav2"，我大概会这样回答：

> 看你需不需要知道"全局"。只需要躲开眼前 0.5m 的东西，反应式足够快、足够省；需要走一条 20m 的迷宫且要接近最短路，就必须有地图和规划。**先用统一指标量出边界，再谈谁更好。**
